# Техническое задание: MarketHub — backend интернет-магазина

## 1. Идея и актуальность

**MarketHub** — готовое серверное ядро для небольшого интернет-магазина электроники: каталог, корзина-заказ, оплата, доставка, отзывы и панель сотрудников. Всё это доступно через REST API, поэтому к нему можно подключить любой фронтенд — сайт, мобильное приложение или Telegram-бота.

**Почему это нужно рынку.** Малый и средний бизнес массово уходит в онлайн, но выбор у него неудобный:

- маркетплейсы забирают значительную комиссию с каждой продажи, диктуют правила и не отдают клиентскую базу;
- коробочные CMS (вроде WordPress + WooCommerce) тяжело дорабатывать под свои процессы, и они плохо масштабируются;
- заказная разработка с нуля стоит дорого и долго.

MarketHub закрывает нишу между ними: это компактный, понятный и расширяемый backend на промышленном стеке (Java + Spring), который магазин разворачивает у себя за один `docker compose up` и дальше развивает сам.

**Чем выделяется:**

1. **Честная складская логика.** Оформление заказа — одна транзакция: остатки списываются атомарно, при нехватке товара откатывается весь заказ, а оптимистическая блокировка не даёт продать последний товар двум покупателям одновременно.
2. **Отзывы, которым можно верить.** Отзыв автоматически получает отметку «подтверждённая покупка», если автор действительно купил товар. Это прямой ответ на проблему накрученных отзывов.
3. **Безопасность из коробки.** JWT, три роли с разграничением доступа до уровня «свой/чужой заказ», BCrypt для паролей, ни одного пароля в репозитории.
4. **Наблюдаемость.** Каждый запрос логируется с уникальным `requestId`, бизнес-метрики (заказы, оплаты, отмены) отдаются в Prometheus — магазин видит, что происходит, в реальном времени.

**Целевая аудитория:** небольшие магазины электроники и аксессуаров, стартапы в e-commerce, команды, которым нужен backend для своего фронтенда или мобильного приложения.

## 2. Роли пользователей

| Роль | Кто это | Что может |
|---|---|---|
| Гость | Неавторизованный посетитель | Смотреть каталог, категории, отзывы; зарегистрироваться |
| CUSTOMER | Покупатель | Управлять своими адресами, оформлять, оплачивать и отменять свои заказы, писать отзывы |
| MANAGER | Сотрудник магазина | Всё, что покупатель, плюс управлять каталогом, видеть все заказы и платежи, менять статусы заказов, делать возвраты, модерировать отзывы |
| ADMIN | Администратор | Всё, что менеджер, плюс управлять пользователями и их ролями, удалять отменённые заказы, смотреть технические метрики |

## 3. Сущности (9 штук) и связи

| Сущность | Назначение | Связи |
|---|---|---|
| User | Учётная запись | ManyToMany → Role; OneToMany → Address |
| Role | Роль доступа | ManyToMany ← User |
| Category | Категория каталога | OneToMany → Product |
| Product | Товар | ManyToOne → Category; OneToMany → Review |
| Address | Адрес доставки | ManyToOne → User |
| Order | Заказ | ManyToOne → User, Address; OneToMany → OrderItem; OneToOne ← Payment |
| OrderItem | Позиция заказа (цена фиксируется) | ManyToOne → Order, Product |
| Payment | Оплата заказа | OneToOne → Order |
| Review | Отзыв о товаре | ManyToOne → Product, User |

Используются все виды связей JPA: `@OneToOne`, `@OneToMany`, `@ManyToOne`, `@ManyToMany`.

## 4. Функциональные требования

### 4.1. Аутентификация
- Регистрация с ролью CUSTOMER, вход по логину и паролю, выдача JWT (HS256, срок жизни настраивается).
- Получение профиля текущего пользователя.
- Заблокированный пользователь не может войти.

### 4.2. Каталог
- CRUD категорий и товаров (MANAGER, ADMIN); чтение — всем.
- Поиск товаров: по категории, подстроке названия, диапазону цен; пагинация и сортировка по любому полю.
- В карточке товара — средняя оценка и количество отзывов.
- Товар, который уже есть в заказах, не удаляется физически, а снимается с продажи (история заказов не ломается).
- Категорию с товарами удалить нельзя.

### 4.3. Адреса
- CRUD своих адресов. Адрес, использованный в заказе, удалить нельзя.

### 4.4. Заказы
- Оформление: список позиций + адрес. Одинаковые товары объединяются, цены фиксируются, остатки списываются, сумма считается на сервере.
- Жизненный цикл: `NEW → PAID → SHIPPED → DELIVERED`, отмена из `NEW` и `PAID`.
- Покупатель видит только свои заказы, сотрудники — все (с фильтром по статусу).
- Покупатель может сменить адрес доставки, пока заказ не отправлен.
- При отмене остатки возвращаются на склад, оплата переводится в статус возврата.
- Удалить можно только отменённый заказ (ADMIN).

### 4.5. Оплата
- Оплата своего заказа в статусе `NEW` (карта, СБП, наличные при получении). Сумма берётся из заказа, а не из запроса клиента.
- Повторная оплата запрещена.
- Возврат средств сотрудником — с отменой заказа.

### 4.6. Отзывы
- Один отзыв на товар от пользователя, оценка 1–5.
- Отметка «подтверждённая покупка» ставится автоматически.
- Редактирует только автор; удаляет автор или сотрудник.

### 4.7. Администрирование
- CRUD пользователей, назначение ролей. Нельзя удалить, заблокировать или лишить роли ADMIN самого себя.
- Пользователя с заказами удалить нельзя — только заблокировать.

## 5. Нефункциональные требования

| Требование | Реализация |
|---|---|
| Java 25, Spring Boot 4.x | Spring Boot 4.1.1 |
| Система сборки | Maven |
| Web | Spring Web MVC, REST, ошибки в формате RFC 9457 Problem Details |
| БД | PostgreSQL 17 (H2 в тестах и dev-профиле), Spring Data JPA, Hibernate 7 |
| Миграции | Flyway (`src/main/resources/db/migration`) |
| Безопасность | Spring Security, stateless JWT (OAuth2 Resource Server), BCrypt, `@PreAuthorize` |
| Тесты | JUnit 5 + Mockito (unit), `@SpringBootTest` + MockMvc (интеграционные), JaCoCo — порог покрытия 70 % (сборка падает ниже) |
| Логирование | Фильтр логирования всех запросов с `X-Request-Id`, MDC, ротация файлов логов |
| Мониторинг | Spring Boot Actuator: health, info, metrics, prometheus, loggers, flyway; бизнес-метрики Micrometer |
| Поставка | GitHub, CI в GitHub Actions, Dockerfile и docker-compose |

## 6. Этапы разработки

1. Создание приложения, сущностей и CRUD-контроллеров.
2. Подключение Flyway, unit- и интеграционные тесты.
3. Spring Security + JWT, логирование запросов, Actuator и метрики.

## 7. Возможное развитие

Корзина с резервированием товара, интеграция с реальным платёжным шлюзом (ЮKassa, CloudPayments), рекомендации товаров на основе истории покупок, уведомления по e-mail или в Telegram, кеширование каталога в Redis, OpenAPI/Swagger-документация.
